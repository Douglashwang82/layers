# Database

PostgreSQL 17 + PostGIS 3.5 locally. The migration runner enables `postgis` before Drizzle migrations. Every domain entity uses UUID keys; join entities use composite keys. Auth session/account/verification are separate tables required by Better Auth. Timestamps are stored consistently on domain and relation tables.

`name` maps to product `nameEnglish` and event `title` at the product concept level; a shared catalog projection keeps card/search rendering small. Product sightings don't imply inventory. Organization verification uses the same explicit verification enum as places and events. Seeded content remains UNVERIFIED, not falsely marked as real verified listings.

Indexes cover city/status places, city/start events, spatial geometry, recommendation uniqueness, product sighting recency, session lookup and user analytics dates. Foreign keys protect referenced entities. Recommendation votes remain one row per user/place when changed. RSVP capacity is enforced by an event row lock in the service rather than a count in the browser.

## Migration workflow

```sh
pnpm db:generate
# Review the generated SQL and snapshot before applying.
pnpm db:migrate
pnpm db:seed
```

Migrations are source-controlled. Do not use schema push in production. Take backups before schema changes. The seed is a single transaction and reuses deterministic UUIDs; it never truncates data. Demo account emails use the reserved `.invalid` domain and have no credential accounts.

All user notes, events, places and sightings start pending. Moderation actions store actor, entity, decision, reason and timestamps. Reports are submissions with a reason. Hidden/rejected/deleted entities are excluded by public repository queries. Deletion in the admin UI is soft deletion, not irreversible purging; add a documented retention and erasure process before collecting real production data.

## Place subject invariants

Local identity for catalog places and provider-referenced businesses (see [the Google Places implementation plan](google-places-implementation-plan.md), P1). Only provider place IDs are stored — never provider names, addresses, photos, ratings or coordinates. Subjects, references and saves use restrictive foreign keys and soft status rather than cascading deletes. Resolution creates the subject and its provider reference in one transaction; a unique-constraint race rolls back the losing subject so no orphan remains, and catalog subjects converge on the unique `catalog_place_id`. A subject is visible only when active, not linked to a hidden/unapproved catalog place, and reachable through an approved catalog place, the viewer's own save, or a layer they may view (public layers additionally need an approved subject city); moderators see all. Review writes lock the subject, then the scope's layer row, then the review. Content, history snapshot, moderation request and analytics commit together. Aggregates are computed from approved rows per scope and never stored. City approval, status changes, catalog linking (which moves external saves to `saved_place` and layer items to `place_id`, refusing conflicts) and provider-ID replacement are revision-checked moderator operations recorded in `moderation_action`. Deleting a layer or group deletes its scoped reviews and their history; retention and erasure rules are still open.

## Membership invariants

Membership is invitation-only (see [the plan](invitation-membership-implementation-plan.md) and [ADR 0001](adr/0001-membership-invitation-auth-transaction-boundary.md)): enforced by DB constraints where possible, plus a `databaseHooks.user.create.before` gate in `apps/web/src/lib/auth.ts` for every account-creation path. `membership_nomination_open_email` (partial unique index) allows only one active nomination per normalized email; `membership_batch_single_open` allows only one open batch; non-legacy admissions require an `invitation_id` (check constraint). A batch's used seats are `redeemed` invitations plus not-yet-expired `issued` ones, computed at query time rather than by a background job flipping status columns. Before cutover to `MEMBERSHIP_MODE=invite_only`, run `pnpm membership:backfill-legacy` (dry-run first) so existing accounts get a `source=legacy` admission row; it identifies real accounts by the presence of an `account` row, since seed/demo users never get one.

Example future nearby query: `ST_DWithin(location::geography, ST_SetSRID(ST_MakePoint(longitude,latitude),4326)::geography, radiusMeters)`. No location history is stored. Current GiST geometry indexes support spatial operations on geometry; add a matching geography expression index if radius queries using that cast become common.
